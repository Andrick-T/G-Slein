# 6. COMPONENT ORGANIZATION

We previously agreed that components should be organized primarily by module, with one global/shared area.

Use:

```text
components/
├── global/
├── auth/
├── patient/
├── doctor/
└── admin/
```

Only create module folders when they actually contain multiple components.

A component belongs in `global/` only if it is genuinely shared.

Examples:

```text
Button
Input
Modal
Spinner
Alert
ConfirmDialog
Pagination
```

A component such as:

```text
PatientAppointmentCard
DoctorPatientQueue
PrescriptionCard
```

should remain module-specific.

### Do NOT:

Create dozens of tiny components merely to satisfy componentization rules.

A component should exist because it:

* is reused
* represents a meaningful UI responsibility
* makes a complex page easier to maintain

# 11. API CLIENT

Create or validate a centralized API client.

Preferred location:

```text
src/services/api.js
```

The frontend should NOT scatter raw requests throughout components.

Avoid:

```javascript
fetch("http://localhost:5000/api/...")
```

everywhere.

Use:

```text
React component
      ↓
API service
      ↓
Express API
```

The backend base URL must come from environment configuration.

Example:

```env
VITE_API_URL=http://localhost:5000/api
```

Use the **actual Phase 6 API contract**.

Do not invent endpoints.

# 13. LOGIN / LOGOUT FLOW

Connect the frontend to the already validated authentication API.

Expected flow:

```text
Login
  ↓
Backend authentication
  ↓
Token received
  ↓
Authentication state stored
  ↓
Current user retrieved
  ↓
Role identified
  ↓
User redirected appropriately
```

Logout:

```text
clear authentication state
clear stored token
redirect to appropriate public page
```

Use the actual backend implementation.

Do NOT modify the backend authentication architecture during Phase 7 unless an actual compatibility bug is discovered.

# 15. PROTECTED ROUTES

Create a simple protected-route mechanism.

Conceptually:

```text
ProtectedRoute
      ↓
Authenticated?
 ├── No → Login
 └── Yes
      ↓
    Role?
      ├── patient → Patient area
      ├── doctor  → Doctor area
      └── admin   → Admin area
```

Role-specific route protection is required.

However:

> Frontend route protection is NOT the security authority.

The backend remains responsible for actual authorization.

Never assume hiding a page makes the API secure.
